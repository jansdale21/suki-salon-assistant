Suki — the Suklay & Kulay salon assistant

A chat assistant that answers customers' questions about a neighbourhood beauty salon, and the operations work that keeps it running safely on AWS.

What the system does

Suki is a website where customers of Suklay & Kulay Beauty Studio (a fictional salon) can ask questions in English, Filipino or Taglish: "How much is a women's haircut?", "Can I rebond and colour on the same day?", "Open ba kayo sa Monday?". Suki answers from the salon's own price list, policies and aftercare tips. It does not book appointments, take payments or give medical advice, and it tells people when it does not know.

Under the hood we did not build an AI model. We took LibreChat, an open-source ChatGPT-style application, gave it a new identity and our own salon content, and connected it to Google's Gemini model on the free tier.

What was wrong with how it was run

Out of the box, LibreChat ran on one laptop with no web address anyone else could use and no HTTPS. Its database had no password, its secret keys sat in a plain text file, and nothing was backed up, monitored or audited. If it broke at 2 a.m. nobody would know, and if the disk died every conversation would be gone. The baseline page records this starting point.

What we changed

  • Made it ours: new name, logo, colours and wording; our own invented salon knowledge base; salon terminology throughout.
  • Put it on AWS: one small EC2 server behind CloudFront for HTTPS, with the salon content in S3 and every key in Parameter Store.
  • Made it observable: a CloudWatch dashboard, 12 alarms that e-mail us, and a log line for every question with its response time and outcome.
  • Made it recoverable: database backups every 6 hours to versioned S3, and a restore that we actually tested.
  • Locked it down: MFA and one IAM user each, no SSH, the server reachable only through CloudFront, phone numbers and e-mails removed before anything reaches the AI provider, CloudTrail and GuardDuty on.
  • Automated the chores: a health check every 5 minutes, a backup every 6 hours and a test-question run every 12 hours, all running unattended.
  • Practised failure: we broke it on purpose (a full disk), found the root cause, fixed it, prevented it, and wrote a runbook.

Trade-off we chose

We optimised for Operational Excellence and Security: everything is defined in code, monitored, alerted and audited. We deliberately accepted weaker Reliability: one server in one Availability Zone, so a server failure means minutes of downtime while we rebuild from code and backups. For a free information assistant for one small salon, that is cheaper and simpler than running two of everything. Details on the Well-Architected review.
