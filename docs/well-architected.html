Well-Architected review

Our setup measured against the six pillars of the AWS Well-Architected Framework: first when the deployment first worked, and again after the incident.

Verdicts: good · adequate · gap.

The "framework asks" lines summarise the framework. The "our system" lines describe what the template and scripts configure. Confirm each one in the console, add evidence links, and set the verdicts yourselves.

1. Operational Excellence

Framework asks: run and monitor the workload, make small reversible changes through code, learn from failures.

Our system: the whole environment is a CloudFormation template; the app deploys from Git (by script or GitHub Actions through SSM); dashboard and 12 alarms; per-request structured logs; automated test run every 12 hours; one incident with a runbook.

First pass (week 2)After WS-F
Partly: everything in code, but no monitoring or runbook yet.Good: dashboard, 12 alarms that reached us by e-mail, structured logs, scheduled tests, one real incident with a tested runbook.

2. Security

Framework asks: strong identity (MFA, least privilege), protect data at rest and in transit, keep traceability, no secrets in code.

Our system: one IAM user each with MFA; instance and deploy roles scoped to our bucket prefixes and parameters; secrets in Parameter Store; EBS and S3 encrypted; HTTPS with a Let's Encrypt certificate on nginx; only 443 and a redirect-only port 80 open, no SSH; CloudTrail (GuardDuty pending AWS verification); PII redaction before the model. Weakness: the server faces the internet directly (no CDN or WAF in front), and GuardDuty is not on yet.

First passAfter WS-F
Partly: MFA and roles done, but secrets still in a local .env file.Good with gaps: MFA, least privilege, Parameter Store, HTTPS, no SSH, CloudTrail; open sign-up is rate-limited; GuardDuty blocked by account verification.

3. Reliability

Framework asks: recover automatically from failure, test recovery, avoid single points of failure, manage quotas.

Our system: containers restart automatically; health check every 5 minutes; backups every 6 hours with a tested restore; rebuild from code. But: one instance in one Availability Zone and a self-managed MongoDB — a single point of failure; the free-tier model quota is a hard limit.

First passAfter WS-F
Weak: no backups, no restore test.Fair: backups every 6 h, restore tested (41 s), health check every 5 min, disk incident prevented. Still one instance in one AZ.

4. Performance Efficiency

Framework asks: choose right-sized resources, measure, and use managed services where they help.

Our system: t3.small chosen after removing search/RAG containers; nginx serves the static branding files; answer latency measured per request (median 1.7 s over 32 test questions on 2026-11-27; live answers 1.5–2.4 s); memory headroom about 50%.

First passAfter WS-F
Unknown: answers took minutes because of model overload.Good for our load: median answer 1.7 s, CPU 3–5%, memory about 50% of 2 GiB.

5. Cost Optimization

Framework asks: pay only for what you use, track spend, tag resources.

Our system: AWS Budget with e-mail alerts; all resources tagged Project=SAM10; free-tier model; lifecycle rules delete old backups; no load balancer or NAT gateway. Biggest costs: EC2 instance and the public IPv4 address. About US$25–30 per month if left running (paid from credits).

First passAfter WS-F
Not tracked.Fair: budget alert, tags, free-tier model; about US$1/day, biggest costs EC2 and public IPv4.

6. Sustainability

Framework asks: minimise idle resources and over-provisioning.

Our system: one small burstable instance; unnecessary containers removed; old Docker images pruned on deploy; logs and backups expire automatically. We do not stop it during grading because backups, tests and the health check need it running; we delete the stack when grading ends.

First passAfter WS-F
Not considered.Fair: one small instance, extra containers removed, logs and backups expire; the instance runs 24/7 during grading, then we delete the stack.

The trade-off and the gap we would fix first

Optimised for: Operational Excellence and Security. Deliberately weaker: Reliability (single instance, single AZ). First gap to fix: the single instance. A daily EBS snapshot through AWS Backup (cheap) would shorten recovery from "rebuild + restore" to "launch from snapshot", and an Auto Scaling group of one would replace a dead instance automatically. We have not done this because it adds cost and complexity beyond the brief's "one or two servers".
